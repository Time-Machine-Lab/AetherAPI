## 背景

`aether-console` 已经允许资产所有者在受保护的工作台中维护上游 URL、请求方法、`authScheme`、`authConfig`、异步任务配置、示例、JSON Schema、代理绑定和 AI 能力档案。Import Agent 计划卡片也已经展示执行关键的资产字段和引导式澄清项。新的后端能力会把固定上游请求头作为仅资产所有者可见的执行配置。

界面必须在视觉和结构上区分三类概念：

- 调用方在 Unified Access 调试请求中输入的请求头；
- 由 `authScheme` / `authConfig` 管理的上游鉴权配置；
- 保存到 API 资产、并由后端调用上游时携带的固定上游请求头。

## 目标 / 非目标

**目标：**

- 在 catalog 与 Import Agent API 类型层映射 `upstreamRequestHeaders`。
- 允许所有者在现有资产编辑抽屉中新增、编辑、移除和清空请求头行。
- 在资产详情中展示仅所有者可见的请求头配置，但不暴露到公开市场页面。
- 在 Import Agent 资产计划卡片中展示计划请求头，并支持针对请求头值的结构化澄清回答。
- 避免在展示中过度突出疑似敏感的请求头值。

**非目标：**

- 不在市场页或 Discovery 契约中暴露上游请求头。
- 不把原始 JSON 编辑器作为请求头的主要交互方式。
- 不支持自定义动态模板、环境变量或按消费者覆盖请求头。
- 不在客户端尝试绕过后端对受保护请求头名称的校验。
- 不提供独立的异步任务查询请求头编辑器，除非后端契约显式增加该能力。

## 决策

### 1. 在资产编辑器中使用 name/value 行

编辑器应把 `upstreamRequestHeaders` 呈现为可重复的行，每行包含请求头名称输入、值输入、移除按钮和新增按钮。空白行会被忽略；清空所有行时按后端契约发送 null 或空值。

相比 JSON 文本框，这种方式更适合小规模结构化列表，用户也不需要记住精确的 DTO 形状。

### 2. 将配置区放在上游配置附近，而不是仅放在鉴权控件中

新配置区应靠近请求方法、上游 URL 和鉴权配置。文案需要明确这些是固定的服务商请求头，不是调用方 API Key，也不是控制台登录令牌。

### 3. 以后端校验作为事实来源

前端可以对明显保留的名称提供轻量提示，但后端校验仍然是权威来源。如果保存因受保护请求头失败，界面应通过现有错误处理展示后端规范化后的错误。

### 4. 谨慎展示所有者请求头

所有者详情可以展示请求头名称和值，因为这些配置由所有者维护。但对于看起来像 key、Bearer token、secret 或长不透明凭证的值，应在现有敏感展示约定允许时进行遮蔽或弱化。市场详情和文档导出不得展示这些请求头。

### 5. Import Agent 将请求头作为一等计划内容展示

`ImportAgentWorkspace.vue` 应在计划卡片的上游与鉴权信息旁展示 `assetPlan.upstreamRequestHeaders`，不得把它们合并进 `authConfig`。如果后端返回稳定的 `targetPath` / `fieldKey` 澄清项，引导式澄清无需新增协议；界面只需清晰标注并通过现有澄清流程提交答案。

## 风险 / 权衡

- [风险] 请求头值可能包含敏感信息。-> 缓解：避免公开展示，在所有者展示中尽量遮蔽可疑值，并依赖后端对流式摘要进行脱敏。
- [风险] 用户混淆鉴权请求头和额外请求头。-> 缓解：拆分配置区与文案；`Authorization` 仍走鉴权配置路径。
- [风险] 后续服务商动态请求头会变复杂。-> 缓解：本次仅支持静态 name/value 行，模板能力留给后续提案。
- [风险] 后端和前端契约落地顺序不一致。-> 缓解：任务要求先更新权威 YAML，映射层在过渡期容忍字段缺失为 undefined/null。
